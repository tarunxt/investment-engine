## Linearization and bounded work

The existing UserModulePreferences owner row serializes selection CAS with enqueue, stage transition, final dispatch and external-effect permission. Disable linearizes at transaction commit. A bounded effect whose fence was acquired first may finish before that commit. Waiting/new work must recheck after the lock. Selection/HTTP owner-lock waits are bounded (2-second PostgreSQL lock timeout/5-second statements); a busy selection returns409 with no partial change. Nothing cancels an already accepted broker order by liquidation.

Selection changes invalidate only the changed module's work version; unrelated module updates do not invalidate active analysis. Streams conservatively reconnect after any aggregate selection epoch change. Queued owned analysis becomes the existing terminal failed status with explicit cancellation reason; running analysis receives a cancel flag and cannot pass subsequent checkpoints. Rebalance parent queued work becomes cancelled. Accepted/completed/frozen outputs, account role, connections and holdings are retained.

Narrow stops, pauses, emergency-stop activation, order cancellation and accepted-order reconciliation are explicitly classified. They retain active owner/operator authorization. Safety cannot clear an emergency stop, resume/start trading, retry an order or submit/redeem/liquidate. Copy/direct safety paths can use an existing warm object but cannot instantiate a new runtime. Reconciliation permits only known read commands; unknown/auth-refresh/write commands close. Existing domain record-state checks remain mandatory.

## Later execution stages must reuse

Persist server-derived owner/module/selection-row version on newly supported work or the existing outbox binding before enqueue. Never use a browser module name, task headers, provider token enumeration or an old allowed result as authority. Unbound legacy optional runtime work remains closed; enabling a public module later requires its separate launch/entitlement/provider gate and versioned resource integration. New transports/effects must use the same classifier/checkpoints/fence, preserve domain idempotency/reconciliation, and add direct/bypassed-UI tests. No new module registry or owner table is needed.

Default entitlement facts remain unknown until a verified source exists; no residence, plan, connection or execution right is inferred from email, timezone, role or stored tokens. operational_enforcement_complete remains false: production/provider readiness and later enabled execution integrations are not asserted by these lifecycle tests.

## Controlled fake work on UAT2

The existing sole executor can run the exact packaged app.uat2.stage07_lifecycle_smoke module with CREDX_UAT2=1 and CREDX_STAGE07_SMOKE_ACK=private-synthetic-only. It creates/removes its own temporary SQLite fixture, blocks every socket connection, and uses fake eligibility only in that standalone process. It checks accepted fake effect, queued cancellation, running fresh denial, foreign isolation, completed history, re-enable and transactional events. It never reads/writes the live database/owner, changes a service flag, calls a provider or creates an endpoint. The real PostgreSQL race/migration gate is separate; neither smoke substitutes for fresh exact-owner ingress/browser/READY/limit verification.
