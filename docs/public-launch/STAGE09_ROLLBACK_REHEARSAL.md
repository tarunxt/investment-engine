It reuses the existing disposable stage09 fixture identity/database and creates no extra roles or GRANTs. The harness refuses execution before any DB connection unless CI/GITHUB_ACTIONS, exact fixed test URL, disposable acknowledgement and /.dockerenv match; it rejects inherited .env files and nonempty initial fixtures. Subprocesses receive a scrubbed fixed synthetic environment, not inherited provider/cloud/libpq settings. All commands are bounded. PostgreSQL service/runner disposal occurs after each job; the script never drops/recreates another database or retries a partially restored fixture.

## Controller findings are NOT fixed by these tests

P1: ctl.py rollback calls pg_restore --clean against existing schema, so new Stage09 FKs can prevent dropping referenced Stage08 users objects after partial clean operations. The PostgreSQL negative case must establish the actual failure signature; migration downgrade/up alone is not restore proof.

P1: standalone rollback does not first create pending-deployment.json. No-DB tests execute the actual unchanged controller with every service/host/subprocess action mocked: injected restore failure performs stop only, never promotion/restart/readiness, but no marker is created and a later start can proceed. The test named `test_known_p1_standalone_failure_leaves_later_start_unblocked` intentionally passes when the existing defect is reproduced. Green CI does not fix or waive this blocker.

When an existing deployment pending marker is present, injected restore failure retains it and actual controller start refuses. This is evidence that the existing lifecycle interlock can protect an already-failed deployment; it is not proof that a standalone rollback from a healthy deployment is safe. No marker/controller was written on UAT2. A separately reviewed runtime repair or explicitly approved guarded operational sequence must establish the marker before any destructive live rollback and remove it only after full successful recovery.

The harness also tests a proposed manual downgrade/restore sequence with an existing test marker: injected downgrade or restore failures retain it and never reach verification/finalization. This helper is test-only, never imported by ctl.py, and uses fake finalization events, not application promotion/restart/readiness. The actual controller has no downgrade step; these tests must not be presented as its implementation or live safety certification.
