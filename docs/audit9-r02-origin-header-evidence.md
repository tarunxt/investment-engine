## Follow-up: native browser and intended transport

The separate `frontend/scripts/audit9-browser-origin-evidence.mjs` now runs installed Chromium 154.0.8037.57 against an actual isolated production Next 16.2.5 build, with a synthetic Auth.js session and a loopback-only mocked backend. Five cases pass: same-origin BFF access translates the HttpOnly session to server-side bearer authorization without forwarding the session cookie; same-origin POST succeeds; a cross-site fetch and a top-level cross-site form POST do not dispatch to the mocked backend; a cross-site top-level GET carries the explicit Lax cookie and succeeds. Browser session output contains neither synthetic provider access nor refresh token. The alternate-site page is local `localhost`, distinct from the application's `127.0.0.1` browser site. No real account or production host participates; browser requests outside loopback are blocked.

This fixture uses an explicitly Lax, HttpOnly, nonsecure cookie over local HTTP. It does not prove production HTTPS Secure-cookie issuance, reverse-proxy headers, cross-subdomain deployment behavior, browser variants, all navigation methods or every action endpoint. It narrows the earlier supplied-session mock result: crossing the native browser cookie boundary matters, and neither CORS simple-POST execution nor a mocked supplied session alone establishes a browser exploit.

Intended-client source review: `frontend/lib/urls.ts` selects the same-origin `/backend-api` proxy in authenticated production browser mode, while server-side calls use the configured server API address; development/local direct transport remains supported. Backend CORS source permits configured frontend origin plus apex/www aliases and explicit localhost development origins. Auth.js Google login and CSP's Kite form destination are specific existing integrations, not authority for arbitrary cross-origin credentialed mutations. Actual production origin values and any independently approved non-browser clients remain unverified. No allowlist, SameSite/auth setting, origin policy or CSP directive was changed.

The repaired original secure-BFF fixture also passes with a synthetic secure-cookie name behind an HTTP reverse-proxy hop. That Node request explicitly supplies the cookie header, so it proves server-side decoding/forwarding, not native browser Secure-cookie transmission. Exact build/commands and unchanged original assertions are recorded under A9-R12. Overall R02 remains partial pending runtime/client scope and compatibility evidence.
